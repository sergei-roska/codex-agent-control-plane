# Efficiency comparison: Codex native subagents vs the A2A runner

Purpose: decide with measured evidence whether the A2A runner is more or less efficient than
Codex native subagents on the same task. Rule: **no efficiency claim without measured results
from the procedure below.** Usage measured here is subscription usage; it is not API cost.
A price table only yields a separately labeled hypothetical estimate.

## 1. Fixture

1. Pick one task with an objective, command-checkable outcome (for example a bounded bug fix
   plus its test).
2. Pin a commit (the output of `rev-parse HEAD` in the source repo) and record it in the
   results file.
3. For every trial create a fresh disposable copy of the repository at that commit in a
   scratch directory (a new clone of the repo, then check out the pinned commit). Never run
   a trial in the working repo. The workspace must be a git checkout so A2A acceptance can
   take a git snapshot (otherwise the disposition is `unverifiable`).
4. Use the identical task prompt text on both sides. Save it verbatim.

## 2. Equal conditions

- Models and effort per role: read them from `profiles/agents/*.toml` (`model`,
  `model_reasoning_effort`) and configure the native subagents with exactly those values.
  Re-read the files at run time; do not copy values from notes.
- Sandbox and permissions: use each profile's `sandbox_mode` (`read-only` or
  `workspace-write`), the same approval policy, and the same hooks and config on both
  sides. Record the effective `permissionConfig` from the A2A artifact metadata
  (`provenance.permissionConfig`) and the equivalent native settings.
- Same account/plan, same Codex CLI and App Server version, no other Codex load during a
  trial, same time of day where possible.
- Same acceptance checks (section 3).

## 3. Acceptance checks

- A2A side: pass the checks through the lead contract, for example
  `npm run ask -- --check '<cmd1>' --check '<cmd2>' "<task>"`. The A2A server executes them
  (no shell, argv split on whitespace) and reports `result.acceptance.disposition`.
  Only `accepted` counts as success.
- Native side: after the session ends, run the same commands (same argv, same cwd) in the
  trial checkout. Success means every command exits 0 and no file outside the intended
  scope changed (`git status --porcelain`, `git diff --stat`).

## 4. Collecting measured usage

A2A (per run, role, and attempt):

```
npm run usage -- --run <runId> [--state <db path>] [--price-table prices.json]
npm run usage -- --task <taskId>
```

Output is JSON: `totals`, `byRole`, `attempts`, `repeatedAssignments`, and
`measured: { basis: "subscription", cost: null }`. Fields: turns, elapsedMs, tokens (sum over
rows with known tokens only; `tokensPartial: true` when any row is unknown), retries,
models/efforts, outcomes, permission denial counts. `null` means unknown, never zero.
Lead-turn rows appear only once the lead graph records them; until then totals cover
workers only and must be labeled so.

`--price-table` takes `{ "<model>": { "inputPerMTok": n, "cachedInputPerMTok": n,
"outputPerMTok": n } }` and adds `hypotheticalApiCost` (known-token rows only, unpriced
models listed). Report it separately, if at all.

Native subagents: token usage must be read from the session's token-usage events. In the
App Server protocol this is the `thread/tokenUsage/updated` notification, whose payload is
`{ threadId, turnId, tokenUsage: { total, last, modelContextWindow } }`; `total` holds
`totalTokens`, `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`,
`reasoningOutputTokens` (see the schema generated by the Codex app-server TypeScript
generator). Sum the final `total` of the parent thread and of each subagent thread. This
document does not assume any on-disk location for these events; if the native session does
not expose them, record tokens as unknown (null) for that trial. Take elapsed time from
wall-clock timestamps around the session, and count model turns from the number of turns in
each thread.

## 5. Procedure

1. Prepare N >= 3 trials per side (same fixture commit, fresh checkout each), alternating
   order (A2A, native, A2A, native, ...) to spread drift.
2. Run the trial, then the acceptance checks, then collect usage.
3. Fill one row per trial in the table; keep raw outputs (usage JSON, native events, check
   logs) next to it.

| A2A    | 1     |                   |             |                                |             |         |               |         |       |
| A2A    | 2     |                   |             |                                |             |         |               |         |       |
| A2A    | 3     |                   |             |                                |             |         |               |         |       |
| native | 1     |                   |             |                                |             |         |               |         |       |

- Repeated work: A2A uses `repeatedAssignments` (null until the journal records objective
  hashes); for native, count subagent tasks whose instructions repeat an earlier one.
- Unknown cells stay "unknown"; never write 0 for a missing measurement.

## 7. Reading the results

- Compare accepted trials only for efficiency; a failed trial is reported as a failure
  rate, not averaged into elapsed or tokens.
- Report per-side median and range over the trials. With N = 3 the evidence is weak; say so.
- Subscription usage is not API cost. Do not present hypothetical API estimates as spend.
- If tokens are unknown or partial on either side, no token-efficiency claim is made.
