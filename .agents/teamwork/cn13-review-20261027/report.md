# CN13 independent review

Verdict: REJECT. Status: complete. Scope expansion: none.

Evidence: read `src/delivery-visibility.js`, `src/backlog-store.js`, `src/task-scheduler.js`, `src/lead-planner.js`, the launcher route and UI, and focused tests; ran `node --test test/delivery-visibility.test.js test/launcher-backlog-ui.test.js` (5 pass); ran a disposable in-memory SQLite probe. The probe inserted two objectives in one project/session, an active claim and planner turn for the shared session, and a queued task with an unmet checkpoint dependency in objective a. The projection for a returned ready=1, active=0, worker capacity 0/1, and planner inFlight=true. No reviewed source or tests were edited.

Blocking:

1. `src/delivery-visibility.js:34-35,48-49,86-87`: A queued task with an unmet checkpoint dependency is counted ready; the dependency appears as unknown in details but is never an admission blocker in `unmet()`. Read: `BacklogStore.#isReady()` requires `checkpointAccepted(...) === true`. Ran: the probe returned ready=1 and blocked=0 for such a task. Fix: distinguish unresolved checkpoint acceptance from confirmed readiness, and count it as blocked or unknown pending an authoritative accepted receipt.
2. `src/delivery-visibility.js:34-35,48-49`: A predecessor task's `succeeded` state is treated as sufficient for every task dependency. Read: `BacklogStore.#isReady()` instead checks `isOutputTrusted()` for `requires_output`/`integration_after`, including matching expected output, and calls `checkpointAccepted()` for the other task edge. A succeeded predecessor with untrusted output is displayed ready. Fix: project the persisted attempt/output and receipt facts by edge kind, using unknown where trust cannot be established.
3. `src/delivery-visibility.js:41-45,69,76-77`: Counts and idle capacity use claims from only the selected objective. Read: `BacklogStore.claimReady()` and `projectCapacity()` use `#liveClaims(projectId)` across objectives. Ran: a claim in objective b made objective a's projection say 0/1 active with no capacity reason, although its only worker slot was occupied. Fix: use project-wide live claims for capacity and role counts; retain selected-objective claim count separately if useful.
4. `src/delivery-visibility.js:63-64`: The planner projection treats a project/session turn as an objective-specific turn. Read: the accepted `delivery_planner_turns` schema has no objective_id, and `LeadPlanner` pins do not store objectiveId. Ran: a turn in the shared session appeared as `inFlight=true` for objective a regardless of origin. Fix: label this as session-wide activity or persist a trustworthy objective identity before attributing it to the selected objective.
5. `src/delivery-visibility.js:18,46,55-56` and `src/launcher-app.js:299-311`: `afterTaskId` is a raw task ID accepted with any objective. Read: task filtering applies the supplied lexical cursor to the newly selected objective with no scope check. A cursor from objective a can skip the first page of objective b. Fix: issue and validate an opaque cursor bound to project, objective, and optional session.
6. `launcher-ui/backlog.js:3-6,36-38,69-72` and `launcher-ui/app.js:259-268`: Main navigation supplies project/session only, while the page requires manual objective ID entry and has no objective discovery. Read: no route/UI hook lists or selects delivery objectives, and no polling or event subscription refreshes a loaded page. An operator opening Backlog from the main UI sees no backlog and an open view becomes stale during work. Fix: add a read-only objective list/selection path and periodic or event-driven refresh guarded by selection generation.
7. `launcher-ui/backlog.js:53-59` and `launcher-ui/backlog.html:17-27`: The team view hides byRole active/limit counts, displays configured objective workerLimit as plain `Worker capacity`, and reduces idle causes to names. Read: actual response includes `capacity.source`, `effectiveRuntimeLimit: null`, role counts, and reason details; UI ignores them. The page therefore cannot show parallel same-role occupancy or why a slot remains idle, and may imply configured capacity is active runtime capacity. Fix: render role counts, known versus unknown effective capacity, and idle reason details without claiming live scheduler admission.

Non-blocking:
- `src/delivery-visibility.js:31-53`: Each request loads all objective tasks and attempts before slicing the page. Query size is bounded but database work is not; consider SQL keyset paging after counts are computed.
- `launcher-ui/backlog.js:51`: Objective stale response suppression is present and passed its focused test; retain it while adding refresh.

Pitfall: Do not infer runnable work or free project capacity from one objective's task states and claims when admission enforces cross-objective constraints.

## Re-review after CN13 rework

Verdict: REJECT. Status: complete. Scope expansion: none.

Read: the revised projection now assesses checkpoint acceptance as unknown, checks task output trust against a succeeded settled attempt and expected output, counts project-wide claims separately from objective counts, labels planner turns session-wide, validates cursor scope, and exposes objective discovery. The UI renders by-role occupancy and configured versus unknown effective capacity. Ran: `node --test test/delivery-visibility.test.js test/launcher-backlog-ui.test.js test/launcher-app.test.js` passed 48/48. Ran: a disposable VM probe of the revised UI with a page carrying `nextCursor` returned three fetches after one poll (initial objectives, initial backlog, refreshed objectives), while backlog count stayed at 1. No reviewed source or tests were edited.

Blocking:

1. `launcher-ui/backlog.js:170,186`: A page with more tasks has a nonempty `cursor`. The 5-second polling path calls `refreshObjectives()`, whose unchanged-selection branch loads backlog only when `!cursor`; thus the main counts, claims, reasons, and task states stop updating indefinitely after the first paginated response. Ran: a disposable VM probe returned one objectives fetch but no backlog fetch on the next poll, with `readyCount` unchanged. Fix: refresh current projection on every poll while preserving or deliberately resetting pagination, and keep request-generation guards.
2. `launcher-ui/backlog.js:95-96` and `launcher-ui/backlog.html:21`: The backend now returns `counts.unknown` for checkpoint and unverified acceptance dependencies, but the summary never renders it. The UI labels `counts.blocked` as "Blocked or waiting", so a queued task with unknown checkpoint acceptance produces Ready 0 / Blocked or waiting 0 although one task is waiting. Read: `assessTask()` classifies it as unknown; UI ignores that count. Fix: show unknown/waiting as its own summary count and label blocked precisely.

Non-blocking: `projectDeliveryObjectives()` exposes at most 100 objectives and only a `truncated` flag; add discovery pagination if projects can exceed that ceiling.
3. `launcher-ui/backlog.css:1,7,10-11`: The new page uses undefined `--text-primary`, `--border-color`, and `--surface` tokens. Read: `styles.css:8,19,24,81-87` defines a near-black body, light `--text-main`, `--border-card`, and dark `--bg-surface`. The fallback makes normal backlog text #20242a on #0a0a0f and sticky headers white, so the backlog is difficult to read and visually inconsistent with the control plane. Fix: use the established theme tokens and verify computed colors in a browser fixture.
