# Process cleanup trace

## Findings

- **Read:** The task runtime uses one shared `CodexAppServer` per active profile, created by `createSwitchingAppServer` in `src/server.js:903` and reused for `run` and `execCommand`. `src/app-server-switch.js:15-24,55-64` tracks aggregate in-flight calls and only swaps/closes the old client when idle (`:27-53,66-88`). This is a service-owned process, not owned by one A2A task.
- **Read:** Every `appServer.run` creates a per-thread run record (`src/codex-app-server.js:853-870`), waits for `turn/completed` (`:1138-1147`, `:917-930`), then deletes the record in `finally` (`:942-946`). `a2a-role-service.js:1001-1018` binds each task's `callRun` to that run and passes a cancellation signal. Task terminal publication occurs on completed/failed/canceled paths (`:1313-1323`, `:1379-1389`); reservations release in `finally` (`:1391-1396`). There is no per-task subprocess registry or cleanup call in this path.
- **Read:** The App Server child itself is detached and leads its own process group (`src/codex-app-server.js:393-398`). On leader exit it SIGKILLs surviving members (`:438-445`); intentional close uses `_terminateProcess` (`:987-1007,1269-1350`). On an unconfirmed abort, it terminates the *shared generation*, explicitly noting collateral interruption of concurrent turns (`:1248-1265`). Therefore a task-completion hook must not terminate the App Server's group: it would violate concurrent-task ownership and budget continuation.
- **Read:** Host `spawn()` for non-sandboxed checks is in `src/acceptance.js:341-420`, detached and killed on leader exit/timeout/abort; agent-proposed sandbox checks instead use `execCommand` (`:427-488`) at lead-run finish (`src/lead-graph.js:3889-3918,3948-3973`). R129 pytest was observed in a role lane; evidence does not identify its spawn mechanism.
- **Read:** `WriterAdmission` persists process identity (`src/writer-admission.js:204-207`) and reconciles unresolved writer groups with identity validation and bounded wait (`:233-250,265-281`). A2A settles writer state after the run (`src/a2a-role-service.js:1065-1072,1324-1329`). This is a workspace admission fence, not a generic task cleanup registry.
- **Read:** Installed generated schema supplied by lead at `/tmp/harness-process-cleanup-schema-20261019` contains `thread/backgroundTerminals/list`, `clean`, and `terminate` requests in `ClientRequest.json:9148-9210` and protocol schemas around `codex_app_server_protocol.schemas.json:1200-1262`. `v1/InitializeParams.json:26-30` declares `capabilities.experimentalApi` default false. `list` takes `{threadId,cursor?,limit?}` and returns `data[]` with `processId`, `itemId`, `command`, `cwd`, optional `osPid`, CPU and RSS (`v2/ThreadBackgroundTerminalsListParams.json`, `...ListResponse.json`). `terminate` requires `{threadId,processId}` and returns `{terminated:boolean}`; `clean` takes `{threadId}` and empty response. These thread-scoped calls provide a native integration seam while preserving the shared server. Source initializes with only clientInfo (`src/codex-app-server.js:483-485`) and has no calls to these methods.
- **Read:** Thread ID is held on task-local `ctx` and run (`src/codex-app-server.js:853-865`) and included in `executionOf(ctx)` (`:1410-1419`). `ctx` has no per-task processId set; thread IDs can be resumed (`:834-849`) and reused, so cleanup must preserve that lifecycle.

## Integration points and lifecycle constraints

- Initialize experimental capability in `_start()`'s initialize params (`src/codex-app-server.js:483-485`) only if protocol support is accepted for the installed server. Native terminal list/terminate/clean requests can be small wrappers over `_request`; exact methods and payloads are in the installed schema above.
- Place cleanup after confirmed turn terminal and before A2A terminal publication (`src/codex-app-server.js:917-946`; `src/a2a-role-service.js:1313-1323`), keyed by that run's threadId.
- On cancel, timeout, rejected start, or generation failure, distinguish confirmed terminal from unknown outcome (`executionOf` exposes `turnTerminal`). A cleanup RPC failure must not make an unknown turn known; report cleanup failure when the generation remains available.
- A thread may be reused for continuation. `clean(threadId)` is broader than targeted terminate; confirm its effect on any still-running terminals before choosing it.
- The observed PID 124021 is explicitly in lane `lane-mvezp50w-e25ac59e`, running pytest; the captured observation is `process-observation.json` at 2026-10-19T08:38:55Z, with parent 124020 and elapsed 741s. The report states R129 ended 08:33:35Z. This is direct evidence of one process outliving role completion, but the preserved snapshot does not include its App Server terminal `processId` or prove which spawn mechanism created it.

## Focused test cases for implementation owner

- Concurrent tasks on separate threads: terminalize one; only that thread's background processes are targeted and the other task continues.
- Targeted termination result false/error: report cleanup failure without changing a completed turn/task outcome or signaling the shared process group.
- Thread reuse/continuation: cleanup after a turn while verifying subsequent `thread/resume` or turn use remains valid; test policy for clean versus targeted termination.
- Cancellation and unconfirmed terminal: cleanup after confirmed cancel; generation crash/unknown outcome must not issue cleanup on a dead generation or mark workspace effects known.
- Experimental API negotiation off/unsupported server: no accidental unsupported request; capability behavior is explicit and tested.
