# AD-03 implementation map

## Dispatch and admission

- READ: The switching wrapper tracks `run`, `prepareThread`, `execCommand`, `resolveExecutionPermissions`, and `readConfig` through `tracked()`; calls increment `inFlight` before invocation and decrement in `finally` (`src/app-server-switch.js:108-182,197-202`). Concurrent worker dispatch uses `appServer.run()` (`src/concurrent-delivery-engine.js:1400-1415`); lead thread creation/rebind uses `prepareThread()` (`:1188-1191,1358-1362`). Lead planner dispatch is also `appServer.run()` with call binding (`src/lead-graph.js:2957-2975`). Legacy orchestrator and role agents share this same project-level `appServer` (`src/server.js:1464-1487`). Thus the existing counter blocks an actual swap during tracked provider work, but does not block *admission* of new calls during a multi-step transition.
- READ: `switchTo()` changes the active profile before checking `inFlight`; it can return `busy` after changing profile (`src/app-server-switch.js:185-195`). The next `settle()` swaps when idle (`:73-80`). Account metadata/limits are plain pass-throughs, not counted (`:216-224`). Any transition needs a separate closed admission gate before profile mutation, and it must cover every engine sharing the wrapper; a one-time `inFlight` check is insufficient.
- READ: `deliveryEngineFence()` fences engine-family changes and workspace writers, but skips same-engine sibling mappings (`src/server.js:432-468`); it is not a transition barrier. Concurrent dispatch itself starts via controller/recovery, and startup recovers planning/executing/draining runs (`src/concurrent-delivery-engine.js:477-501`).

## Durable evidence and predicates

- READ: Existing project SQLite state includes objective dispositions/control pins and budget waits (`src/backlog-store.js:949-1027`), claims (`:1554`), attempts, planner turns and planner recovery rows (`src/lead-planner.js:108-128`; `src/concurrent-delivery-engine.js:1117-1125`), dispatch/call-binding journal (`src/durable-store.js:93-128`), candidate intents (`src/candidate-store.js:224-232`), output publication/binding rows (`src/delivery-output-artifacts.js:138-150`), writer executions, concurrent mappings and fence projections (`src/server.js:211-228,432-468`). Dispatch journal states submitting/submitted/finished and call bindings are per-call provenance, not a provider-transition journal.
- READ: No durable provider-transition intent/state table or startup recovery path is present in the inspected source. `planner.provider_rebound` is appended transactionally with run binding and wake after thread preparation (`src/concurrent-delivery-engine.js:1203-1235`), so it records completed rebind only, not intent before switch. Strict provider pin remains enforced; identity capture binds a fixed `codexHome` (`src/delivery-provider-identity.js:40-48`; engine construction uses pinned getter at `src/server.js:1499-1513`).
- READ: Closest reusable fail-closed predicate is `#providerResumeEligibility()` (`src/concurrent-delivery-engine.js:1098-1126`): exact objective disposition/control owner-generation/revision, no owner decision or pending inbox, no controller/planner/scheduler activity, no active/expired/fenced claims, all attempts terminal plus effects settled, all planner turns complete/stale/reconciled, no unsettled planner recovery, and no pending lifecycle retry/wait. `shutdownProjection()` adds admission stopped, unresolved claims/attempts, planner turns/inFlight, inbox, effects and stopped disposition (`src/delivery-lifecycle.js:364-397`). Server `deliveryEngineFence` adds sibling mappings, writer executions and candidate/publication checks (`src/server.js:432-468`). These are objective-scoped / cross-engine proofs; none alone establishes quiescence of all same-engine siblings. Project-wide transition gate must enumerate each mapped objective and fail closed on unknown/missing proof, then also require wrapper `inFlight===0`.

## Async availability and minimal sequence

- READ: `budgetWakeEligibility` is synchronous, defaults false, rejects a thenable, and only wakes on literal `true` after due time and pin checks (`src/delivery-lifecycle.js:37-63,117-138`). `tick()` is synchronous and drives due waits (`:199-228,442-457`). Keep this contract. Safe integration is an async preflight/recheck in engine/server orchestration: query authoritative account/model limits; if suitable, persist/enter transition; after awaits re-read wait state and owner/control pins; only then perform transition, fresh thread preparation, and atomically commit lineage plus wake. Do not pass async eligibility into lifecycle.
