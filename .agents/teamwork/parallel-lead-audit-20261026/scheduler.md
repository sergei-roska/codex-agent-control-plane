# Scheduler trace

Evidence is from source read on 2026-10-26; no runtime test was run.

- Multiple writable worker turns can run concurrently when isolated-lane mode is enabled. `server.js:918` passes `worktreeMode` as `parallelWriters`; `lead-graph.js:2752-2754` enables concurrent waves only with this flag. Assignment records get execution-group indices (`lead-graph.js:3420-3421`); grouped dispatch submits every pending item in the lowest eligible group (`3512-3522`) concurrently (`3736-3744`). The A2A role service selects a lane for eligible workspace-write tasks (`a2a-role-service.js:860-863`), and only the fallback non-lane writer path acquires admission before running its turn (`913-930`). Lane turns therefore do not hold the global writer admission while the worker edits its isolated copy. Each completed lane must acquire workspace-wide admission to apply its patch (`writer-lanes.js:416-425`); so model turns can overlap, while shared-workspace integration is serialized. In non-worktree mode writable assignments are selected one at a time (`lead-graph.js:3522`), array order, irrespective of wave (`2754`).

- Same-role concurrency is not blocked by role identity. The per-service reservation map rejects a duplicate *taskId* already executing (`a2a-role-service.js:414-423`), not a second task for that role. Thus two assignments routed to the same role can execute simultaneously if scheduler grouping permits; for writers, workspace admission may serialize their actual write turns. Default admission is one workspace-wide `WriterAdmission` shared by registered role agents (`a2a-role-service.js:1470-1472`), so writable role turns do not concurrently acquire shared workspace access. Read-only same-role tasks have no such writer admission cap. This source search found no per-role concurrency limit.

- Lead planning waits for the whole current batch/group to settle. `collect` polls all submitted items with `Promise.allSettled` (`lead-graph.js:3786-3794`); graph edges go dispatch -> collect, and collect routes to dispatch only if batch items remain pending, otherwise verify (`4536-4537`, `4480-4487`). Verification then routes to decide (`4489-4497`). There is no lead `decide` node while submitted workers are still being collected.

- Early worker completion does not free a slot for new lead planning. A grouped batch may dispatch a later group after prior group items are finished (`3517-3522`), but no new assignment is planned until the batch has no pending/submitted items, verification completes, and route returns to `decide` (`4480-4497`).

- Clarification on completion: `collect` polls every submitted item with `Promise.allSettled`, and each `pollItem` waits until the corresponding A2A task is terminal (`lead-graph.js:3747-3774, 3786-3794`). Therefore the scheduler does not integrate/process group outcomes as each task first finishes. Once the whole submitted set has settled, the graph routes to dispatch if pending group items remain; `dispatch` then processes all finished unprocessed items through `integrateFinishedGroup` (`3480-3483`). Separately, each A2A lane service integrates its own patch before it reports task completion (`a2a-role-service.js:1078-1095`), under serialized writer admission (`writer-lanes.js:416-425`).

- Architectural constraints: scheduling is batch/group scoped; lane writers execute in independent copies but workspace admission serializes their patch integrations (`writer-admission.js:40-44, 74-75`); one unresolved writer prevents further writable dispatch (`lead-graph.js:3523-3524`). Configuration: `parallelWriters` is wired from `worktreeMode` (`server.js:918`) and defaults false at orchestrator construction (`lead-orchestrator.js:234`). Caller `maxRounds` is optional/configurable (`lead-orchestrator.js:220-221`), not a concurrency limit. No fixed role-level concurrency number is present in inspected code.
