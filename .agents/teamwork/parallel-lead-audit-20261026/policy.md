# Policy trace: parallelism and autonomy

## Findings

- **Confirmed mismatch risk (read):** the active `/home/sr/codex-home/lead-policy.md` calls for cohesive delegation, a smallest sufficient team, no unnecessary gates, and resolving routine uncertainty without asking the user (lines 14-16, 37-43, 73-79). The separate `/home/sr/codex-home/agents/lead-policy.md` is stale and materially conflicts: its lines 3-5/13-24 prescribe lead-only architectural decisions, a fixed role/model ladder, and proactive dispatch; do not use it as active policy. `agents/worker.toml` instead says small scoped changes and "Do exactly what [the brief] specifies" (lines 7-13), but also explicitly requires owning routine choices, continuing independent work, and stopping only for real ambiguity (lines 32-37, 46-63). Those rules do not mandate a worker stop on every uncertainty.

- **Confirmed runtime cause for serial writer behavior (read):** `profiles/TEAM.md` explicitly says same-wave parallel writers require isolated workspace copies and disjoint files (lines 11-15). The lead prompt explains the runtime branch: when `deps.parallelWriters` is false, writable assignments run one at a time in array order regardless of wave; when true, independent disjoint writers should share a wave (src/lead-graph.js:2752-2754). `src/lead-graph.js:3512-3522` uses groups only when parallelWriters is enabled; otherwise it dispatches one pending item. This is runtime gating, not merely model prompting. The actual setting is external to this trace, so whether a given run had the feature enabled remains unverified.

- **Plausible prompting effect, not mandatory microsteps (read):** lead prompt asks for a "smallest coherent change" indirectly through role briefs and the worker profile says "small scoped change" (worker.toml:2,10); but active policy says several small changes go in one brief and explicitly says avoid unnecessary repeated reviews (lead-policy.md:38-40, 75-77). Harness instructions directly counter micro-diffs: batch related changes into one verification task and avoid splitting shared-state work into micro-diffs (profiles/TEAM.md:47-55,80-88). If observed microsteps occur, likely causes are lead decomposition choices or the active client's prompt loading, not a rule requiring one-file assignments.

- **Review serialization is partly mandatory by design:** material changes need verifier after integration; only designated critical/performance/milestone/blocker cases need auditor, and ordinary round endings do not trigger audits (profiles/TEAM.md:47-76). Verifier and auditor must inspect an integrated candidate in later waves (profiles/TEAM.md:90-99). Critical verifier then auditor ordering is an actual gate, as is routine verifier acceptance; neither implies an auditor on every task. `src/contracts.js:895-908` groups consecutive equal non-null waves, and `:925-943` prohibits reviewer/writer sharing a group. This supports serial review of a candidate, not serial independent implementation.

- **Premature stops and user questions are not intended policy (read):** active policy says task size alone never requires approval and blockers go to lead while independent work continues (lead-policy.md:40-43). Harness team says agents do not ask the user; lead investigates and resolves reversible choices, asking only for missing authority, irreversible/external actions, or materially different product outcomes (profiles/TEAM.md:17,21-25). Runtime prompt says investigate before asking and finish false triggers further investigation; with unlimited rounds by default (src/lead-graph.js:2758-2762). A partial ledger can finish immediately only when explicitly supplied with a false-goal finish (src/lead-graph.js:3167-3169); therefore the prompt permits premature partials, but does not require them.

## Bounded interventions

1. Make the single active lead policy explicitly call for one cohesive package when scope and acceptance boundary are shared, concurrent disjoint writers in one wave when enabled, and staged writers only for dependencies/gates. **Tradeoff:** clearer autonomy, but still constrained by runtime capability and review gates.
2. In lead prompt/decision recovery, require the lead to check whether remaining blockers can be removed by its own investigation, an authorized worker, or safe parallel work before choosing partial; preserve the existing true owner-only path. **Tradeoff:** fewer premature finishes, potentially more turns.
3. Keep review gates but foreground exact conditions that trigger routine verifier vs gated auditor, including reuse of valid receipts. This addresses serial-review overapplication without weakening required acceptance. **Tradeoff:** slightly more prompt complexity.
