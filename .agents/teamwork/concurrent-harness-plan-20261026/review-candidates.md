# Review and candidate concurrency map

## Source-backed current behavior

**Candidate identity is content and contract scoped, not a durable candidate object.** `computeReviewTarget()` hashes every file under declared review paths (including missing paths and in-workspace symlink targets), run ID, review kind/checkpoint/reason/paths/evidence/prerequisite IDs, goal, requirement context, pinned-check argv and current pin hashes (`src/review-policy.js:59-155`). It returns unknown on unreadable/escaping scopes, traversal limits, or unavailable check pins. `sameReviewScope()` fixes kind, checkpoint ID, reason, sorted paths/evidence IDs and prerequisite IDs (`:28-37`). Receipts are accepted only against the current known identity; latest matching receipt and trusted completed role outcome are required (`src/lead-graph.js:1522-1560,1611-1641`). Routine receipts require verifier; gated kinds require verifier plus auditor on finish (`:1729-1765`). Auditor must see the current target, and for non-pinned gated reviews needs a matching accepted verifier receipt (`:3634-3648`).

**Integration invalidates receipts deliberately.** Worker outcomes are integrated before review receipt processing. A receipt is rejected/stale if captured target differs from the new current target; receipt records include identity, role, status and attempt IDs (`src/lead-graph.js:2368-2374,2436-2554`). Repair preserves old history but only reuses it after unchanged review context, target identity, settled integrated effects, complete attested delta and no scope violations; otherwise it advances the receipt floor and requires fresh review (`:2374-2433`). Partial finish exempts only ledger-blocked/not-started and owner-deferred obligations; accepted ledger items remain gated (`:1723-1727,3160-3169`; test `test/lead-graph.test.js:5944-5967`).

**Critical gates are globally conservative.** `gateFailure()` rejects any writable assignment unrelated to each incomplete critical checkpoint, except its matching review/repair or the narrowly linked prerequisite verifier (`src/lead-graph.js:1694-1753`). Dispatch repeats the guard per writable item (`:3683-3695`). The linked-verifier exception deliberately permits only one new scope, exact complete pending checkpoint IDs, and no co-dispatched writer (`:1703-1721`); prompt says do not combine linked scopes (`:2747`). This serializes unrelated implementation behind a pending critical audit even when file scopes do not overlap. It protects the invariant that no later write invalidates an in-flight review and that dependent writes cannot bypass an unmet gate; the current model does not express/validate dependency edges fine-grained enough to relax globally.

**Parallel waves exist, but are gated by runtime mode and grouping.** Consecutive equal non-null `wave`s form a group; null is a singleton (`src/contracts.js:895-908`). Writers sharing a group must have disjoint scopes and reviewers cannot share a group with writers (`:925-943`). With `deps.parallelWriters`, grouped items dispatch together and next group waits for prior group completion; without it, one item dispatches at a time regardless of wave (`src/lead-graph.js:3512-3524`; `test/lead-graph.test.js:3723-3792`). The design doc says this flag is enabled only after worktree isolation probe/mode checks pass (`docs/parallel-writers-design.md:24-52,54-77`). The no-group legacy batch also remains serial (`test/lead-graph.test.js:3794-3813`). `batch.parallel` is only automatically true for all-read-only, no-review-role, no-explicit-wave batches (`src/lead-graph.js:3414-3422`), so repeated reviewers require explicit compatible grouping and parallelWriters; same-role identity is not itself a blocker. No live setting was inspected; actual runtime mode is unverified.

**A writable verifier is a deliberate exception, not general reviewer concurrency.** Role profiles make verifier workspace-write while auditor is read-only (`profiles/agents/verifier.toml:3-12`, `profiles/agents/auditor.toml:3-12`). The graph accepts verifier writes only for test/check paths with attested isolated-lane effects; otherwise it may not satisfy review result validity (`src/lead-graph.js:2459-2478`, `src/review-policy.js:207-235`). A verifier in a writer group is forbidden by wave validation, and unresolved writer effects block review (`src/lead-graph.js:3634-3636`). Do not fix this by broadly making verifier writable or by trusting its self-reported checks.

**Acceptance and preflight are shared-workspace operations.** Preflight reports route/capability availability only, explicitly not dependencies, outcomes, receipts, or CI evidence (`src/verification-preflight.js:137-173`). `runAcceptance()` acquires writer admission, snapshots workspace, checks pinned script hashes, and runs sandboxed agent checks through App Server; changed pinned checks fail pending integrity review (`src/acceptance.js:656-739`). Candidate verification later compares current git fingerprint with the accepted fingerprint (`:780-815`). Acceptance is therefore a serialized final boundary over the integrated candidate; preflight cannot stand in for it. Existing isolated worktree design supplies private lane candidates and serialized admission/mutex integration; its design calls out lane confinement, unsafe patch refusal, scope enforcement, crash reconciliation and no integration on canceled/failed/unknown turn (`docs/parallel-writers-design.md:24-35,79-153,214-228`).

## Recommended target boundary (design, not current behavior)

Introduce immutable candidate records (`candidateId`, `baseCandidateId`, content/tree digest, created-from assignment, declared changed paths, status, evidence refs). Bind every review receipt to candidate ID/digest plus immutable review context hash. Review workers read a frozen candidate mount/snapshot; no reviewer reads a moving shared tree. Keep the current context dimensions (goal/requirements/check pins, review scope, run) in the identity. Represent work dependencies as explicit edges over task/checkpoint IDs and declared read/write scopes. Permit concurrent writers/reviews only where dependency closure is satisfied and declared write scopes are disjoint; unknown scope, unknown candidate, or unresolved effects fail closed.

For each ready wave: atomically claim distinct backlog items; run independent writers in private lanes; collect/refuse patches and serialize integration under existing admission/mutex; create a new candidate revision after integration. Reviews of independent already-frozen candidate revisions may run concurrently. If integration changes a candidate's dependency closure, invalidate only receipts whose declared read/dependency scope intersects changed content; preserve old receipts as historical, never relabel them current. A gated checkpoint's dependent tasks stay blocked until its matching candidate has accepted verifier/auditor receipts. Independent tasks may continue on a declared base candidate but cannot silently rebase onto unreviewed changes. Final acceptance remains one serialized check against the exact integrated candidate fingerprint, with current owner checks/permissions and no unresolved writers. Final finish requires accepted checkpoints or an honest blocked/not-started ledger; owner deferrals remain typed decisions, never inferred from a partial finish.

Prerequisites before relaxing global gates: immutable candidate storage and replay-safe IDs; review consumers guaranteed to read that exact snapshot; explicit dependency/read-set completeness (unknown means global barrier); integration conflict detection and atomic revision creation; review invalidation on intersecting changes; persisted claims/leases and completion events; cancellation/restart reconciliation; candidate-bound owner acceptance; bounded retry/review recovery and budget accounting. Without these, existing global barriers and serialized acceptance are correctness protections, not just throughput costs. Current bounded review recovery limits generations to two, with one extra only by owner grant (`src/lead-graph.js:56-62`); retain the cap per checkpoint and never turn a failed reviewer into acceptance.

## Adversarial acceptance scenarios for implementation

1. Two disjoint writers/checkpoints in one project run concurrently, with candidate-bound receipts; separately configured distinct projects also run simultaneously without sharing review receipts or check pins.
2. Two writers declare disjoint paths but one reads the other's output (or omits a read dependency): scheduler must require an edge or reject/serialize on unknown dependency; no stale review is accepted after rebase.
3. A candidate changes within a review's declared dependency closure while auditor is running: that receipt becomes stale; unaffected candidate receipt remains reusable only if digest closure is unchanged.
4. A writer crashes after patch admission/integration begins: recovery proves process quiescence and either records exact integrated candidate or leaves effects unresolved and blocks dependent reviews/finish.
5. One of two parallel reviewers fails, times out, or hits usage limit: successful independent receipt persists; only failed checkpoint retries within bounded recovery; no global duplicate rerun unless target changes.
6. Writable verifier writes an allowed test file: candidate/review scope and check pins change; it cannot certify the pre-write candidate, and a fresh verifier/auditor path is required as applicable.
7. Owner defers one checkpoint while another is accepted: defer blocks only named checkpoint; accepted checkpoint still requires current receipts; ledger cannot mark unreviewed work accepted.
8. Owner acceptance races integration or an unresolved writer: admission serializes it; a later integration invalidates its fingerprint. A Codex session quota pause stops new turns across projects, while a project-local deferral affects only its project/run.

Existing source tests to extend: review identity/path and symlink cases (`test/review-policy.test.js:12-80`); wave order and runtime-off serialization (`test/lead-graph.test.js:3723-3848`); review freshness/recovery (`:4110-4155,4520-4549`); partial ledger gates (`:5944-5968`); pinned check mutation (`test/acceptance.test.js`, tests named `check_changed` / `check_weakened`); lane conflict/scope/crash cases (`test/writer-lanes.test.js`, inspect current names before implementation). Proposed scenarios above are acceptance requirements, not evidence that parallel candidate review currently works.

## Multi-project isolation and shared limits

**Source facts:** Launcher project identity is SHA-1 of canonical real path; adding a symlink alias resolves it first, so it maps to the same project ID (`src/launcher-projects.js:64-65,364-380`). Each project record has its own server port, state DB and settings location (`:334-345,378-383`); launcher usage queries open the requested project's DB (`src/launcher-app.js:259-279,304-312`). The server constructs `WriterAdmission` against that project's DB and workspace (`src/server.js:877-898`). Admission and lane mutex use canonical workspace paths; the cross-process workspace lock instead uses Git common-dir identity, intentionally making nested workspaces in one repository contend (`src/writer-admission.js:45-75`, `src/durable-store.js:220-242`, `src/writer-lanes.js:88-100,255-275`). Review targets include `runId` and current project workspace content (`src/review-policy.js:59-155`); assignment/attempt IDs and usage rows are run/context-keyed (`src/durable-store.js:29-30`, `src/usage-ledger.js:8-38`). These are real isolation boundaries to preserve.

**Design consequence:** First deliver single-project backlog and candidate/review concurrency; retain existing independent project servers, with no cross-project fairness broker prerequisite. Put project ID and canonical workspace identity on tasks, candidates, receipts, claims and recovery events. Different runs share workspace reconciliation but never imply project-wide approval. A symlink alias resolves to the same project; distinct roots and Git common dirs are separate concurrent projects. Nested roots or project records sharing a Git common dir must share writer admission/candidate lineage or be rejected as duplicates. Do not deduplicate by display name.

Owner checks, permissions and scratch stay project-bound; never borrow check pins or receipts. The active Codex policy applies its 90% five-hour threshold to new dispatches across the session; another provider's exhaustion blocks only its calls (`/home/sr/codex-home/lead-policy.md:30-35`). This account/session throttle does not merge backlogs or stop running tasks. Harness usage is project DB and run/context scoped (`src/usage-ledger.js:8-38,97-115`); no Harness global quota allocator was found. Actual quota and runtime configuration were not queried.
