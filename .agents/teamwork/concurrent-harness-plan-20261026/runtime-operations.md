# Runtime, lifecycle, and observability map

Evidence labels: **Source fact** means read from the cited implementation; **Recommendation** is a proposed planning implication; **Unverified** means the source does not prove a runtime/provider behavior. No runtime probes or tests were run.

## Runtime and project ownership

- **Source fact:** Launcher `createProjectManager` stores project metadata in `.runtime/projects.json`, assigns a port from 3000-3099, and assigns a project state DB (first project can inherit legacy `.runtime/state.sqlite`; later projects use `.runtime/projects/<id>/state.sqlite`): [src/launcher-projects.js:81-103, 143-155, 325-353, 364-391]. `start()` spawns one `server-bootstrap.js` child per project with distinct `PORT`, `CODEX_WORKSPACE`, `CODEX_A2A_STATE_DB`, role override path, and project settings path [src/launcher-projects.js:412-467]. Thus separate projects already have separate lead graphs, task stores, checkpoints, journals, sessions, and state DBs. Launcher exposes project start/stop/status APIs [src/launcher-app.js:146-195].
- **Source fact:** State DB holds A2A tasks, SQLite LangGraph checkpoints, dispatch journal, usage ledger, activity, session thread metadata, recovery state, and other project records. The DB is WAL/FULL synchronous and held through one shared connection; separate kernel locks protect a state file and workspace [src/durable-store.js:118-159, 163-209, 220-225]. Workspace lock identity is the Git common directory, so two server processes on separate worktrees of one repo still contend for one workspace lock; this is a real startup prohibition, not just UI contention [src/durable-store.js:211-225; test/server.test.js:1133].
- **Source fact:** Account profiles default to shared `~/.codex-a2a/accounts/accounts.json`; each project server constructs its own switching App Server but reads that profile file for the active home [src/account-profiles.js:30-47; src/server.js:832-838]. Launcher account activation writes the shared active profile [src/account-profiles.js:111-120; src/launcher-app.js:898-909]. Each server's `createSwitchingAppServer` only tracks its own in-flight requests when swapping homes [src/app-server-switch.js:14-16, 45-75]. A project-local auto-switch updates global profile selection; other project processes are not coordinated by that wrapper and observe profile changes on their own later requests. **Unverified:** provider quota is account-wide, but no project-wide or launcher-wide quota broker/fair scheduler is present in these paths.
- **Recommendation:** Keep backlog and worker scheduling project-scoped; preserve multi-project child/process/state separation. A global capacity broker is not required for first delivery, but account identity/quota should be represented as shared resource attribution, not silently assumed project-local. Avoid same-repository multi-process deployment until workspace-lock policy supports it.

## Worker and lead concurrency

- **Source fact:** `LeadOrchestrator` owns a LangGraph instance and run-keyed `runtimes`; distinct task IDs can be active concurrently, while `makeLeadExecutor` and middleware reserve only by task ID [src/lead-orchestrator.js:278-318, 371-393; src/server.js:317-319, 708-739]. Specialist endpoint executors also reserve by task ID, not role-wide; role executors are instantiated once per role route [src/a2a-role-service.js:365-368, 403-425, 1456-1503]. There is no general max worker count or global role semaphore in these interfaces. The lead graph's scheduler determines assignments/waves (see scheduler trace).
- **Source fact:** `CodexAppServer` maps active runs by thread ID, supports concurrent distinct thread runs and explicitly rejects an overlapping run for the same thread [src/codex-app-server.js:187-194, 1018-1030; test/codex-app-server.test.js:409,649]. Each project has one App Server child at a time [src/codex-app-server.js:403-419]. Writer admission serializes shared-workspace writers across roles; read-only work can overlap. Parallel writer lanes are enabled only when startup isolation mode allows it [src/a2a-role-service.js:928-957; src/server.js:895-907, 924-926; test/a2a-role-service.test.js:583].
- **Source fact:** One lead Codex thread is persisted per A2A `contextId`; it is reused on subsequent session turns only if profile hash, Codex home, and token rollover check allow it [src/session-threads.js:3-6, 52-100; src/lead-graph.js:2901-2922, 2978-2991]. Concurrent distinct lead task IDs sharing a context are not serialized by context ID, yet can select the same persisted thread and be rejected by the App Server same-thread guard. Worker attempts carry per-attempt task/context IDs and continuation metadata; continuation reuses the prior thread only when lane/home/MCP pins remain compatible [src/a2a-role-service.js:467-495, 1026-1056].
- **Recommendation:** Worker instances need stable distinct attempt/thread identity and a per-session lead claim or serialized session-turn queue. Maintain task-ID idempotency while separating role capacity from same-task duplicate rejection. Do not equate writer admission capacity with total worker capacity.

## Pause, cancellation, budget, and restart boundaries

- **Source fact:** UI soft pause calls project control endpoint; it sets a lead pause flag and parks at a safe graph boundary, and explicitly does not cancel worker turns [src/launcher-app.js:375-399; src/server.js:757-789; src/lead-orchestrator.js:367-384; src/lead-graph.js:4316-4319]. Canceling a pause request only withdraws the pending flag. A2A cancellation aborts a worker Codex request; confirmed stop is needed, and unconfirmed cancellation can terminate the shared App Server child, disrupting sibling turns [src/a2a-role-service.js:425-435; src/codex-app-server.js:1486-1503; test/codex-app-server.test.js:940]. Lead cancellation fans out through graph cancellation and waits for downstream A2A confirmation [src/lead-orchestrator.js:489-535; test/lead-orchestrator.test.js:235,419].
- **Source fact:** Budget watcher is process-local and watches only lead tasks persisted as `INPUT_REQUIRED` whose LangGraph checkpoint pause is exactly `waiting_for_budget`; timers/cache/history are memory-only [src/server.js:1038-1057; src/budget-watcher.js:68-89, 216-276]. Its model set is the union of configured role models and lead model [src/server.js:953-975]. A worker usage-limit result can retain continuation metadata and be aggregated into graph `budget.source='worker'`; lead budget exhaustion returns `budget.source='lead'`; both reach the budget interrupt [src/lead-graph.js:3864-3881, 4322-4329, 2961-2968]. Auto-resume then checks limits and may switch account before resuming the lead via the normal A2A message path [src/budget-watcher.js:131-165, 175-214; src/server.js:1070-1094]. Individual worker tasks are not independently budget-watched.
- **Source fact:** Server startup reconciles submitted/working lead tasks to resumable `INPUT_REQUIRED` restart pauses, but marks in-flight specialists failed because effects may be unknown [src/server.js:878-879; src/durable-store.js:432-467]. Server shutdown stops watchers, aborts active leads with an owner-stop reason, waits up to 5 seconds for quiescence, then closes App Server/HTTP within another 5 seconds [src/server.js:999-1016; test/server.test.js:1087]. Launcher sends SIGTERM and only falls back to SIGKILL after 12 seconds [src/launcher-projects.js:19-23, 300-305, 552-559]. Thus lead checkpoints survive restart, but running worker execution is not replayed as live.
- **Recommendation:** Durable backlog state must outlive process-local watcher/runtime maps. Project-scoped pause/cancel must address task/claim IDs explicitly; preserve current lead safe-boundary pause semantics and distinguish cancel request from confirmed worker quiescence.

## UI and observability contracts

- **Source fact:** Main UI uses HTTP polling, not an SSE stream: project list every 3 seconds, server/session refresh from 1-second `updateStatus`, usage refresh throttled to 10 seconds; session API reads task rows + dispatch journal and joins live activity by worker task ID [launcher-ui/app.js:392-445, 1016-1043, 1740-1742; src/launcher-sessions.js:122-149]. Activity rows are best-effort in the project state DB; updates are throttled to 2 seconds and include phase, one-line summary, commands, edits, timestamps [src/activity-store.js:3-7, 10-24, 95-140, 160-240]. UI displays active workers, objective, activity, idle age [launcher-ui/app.js:663-725].
- **Source fact:** Usage ledger rows are stable-keyed, per turn, and include role/task/attempt, elapsed/startup/queue wait, token provenance and outcome [src/usage-ledger.js:3-44, 80-99]. Session performance API preserves the default usage response and adds performance only with `?details=performance` [src/launcher-app.js:303-326; test/launcher-performance.test.js:158]. Separate performance collector writes `performance_attempts` and an atomic `task-metrics/v1` snapshot [src/performance-store.js:118-162, 358-423]; performance UI prefers that snapshot then falls back to session usage/task APIs and refreshes every 30 seconds [launcher-ui/performance.js:346-389, 422-428].
- **Gap / source fact:** These are session/attempt histories and live turn activity, not a durable backlog or global worker-pool view. There is no source API for queued-ready count, claim leases, role capacity/saturation, cross-project active workers, fairness, or scheduler latency. `queue_wait_ms` records writer admission wait, not time waiting for planned assignment or worker slot. Launcher `/status` logs are bounded in-memory chunks; startup diagnostics are persisted separately [src/launcher-projects.js:94-95, 115-118, 161-212; src/launcher-app.js:189-195].
- **Recommendation:** Preserve existing session/task/usage endpoint shapes; add backlog/capacity projections as additive, project-qualified APIs and UI panels. Polling clients must retain project/session selection behavior, abort stale project requests, tolerate older DBs with missing optional tables, and treat unknown measurements as null. Session/task deletion currently requires terminal state and refuses unresolved writers/active lanes [src/launcher-sessions.js:213-265, 268-279]; backlog deletion/migration must honor equivalent claim/execution safety.
