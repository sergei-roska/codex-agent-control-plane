- **Source fact:** Core profile TOMLs currently set engineer, explorer, and verifier to gpt-6-luna / high; auditor is gpt-6.1-sol / high [profiles/agents/engineer.toml:1-6; explorer.toml:1-6; verifier.toml:1-6; auditor.toml:1-6]. - **Source fact:** Project overrides are version 1 JSON in each project's runtime directory; allowed fields are only model, effort, extraRules, all optional. Empty values mean profile default; unknown fields invalidate the document and lead to all overrides ignored. Writes are atomic, and role overrides are only editable while project server is stopped; server loads them once at startup [src/role-overrides.js:3-15, 24-80, 104-149; src/launcher-app.js:576-629].
- **Source fact:** GET /api/projects/:id/team returns effective role model/effort, profile defaults, overrides, and models as the sorted unique model strings configured in base roles (not an account model catalog) [src/launcher-app.js:580-605]. Role cards show model and effort chips [launcher-ui/app.js:1744-1805]. - **Confirmed selector finding:** Source maps the model and effort selectors to separate fields; I cannot confirm a literal swapped-field/render defect. The confirmed gap is stale/static capability data: model choices come only from configured role profile names and effort choices are global, rather than model-specific App Server discovery. Current validator also rejects non-gpt model identifiers even though protocol model is a string [src/role-overrides.js:37-47; src/role-catalog.js:113-115].

## Installed protocol evidence and Fast controls

The schema does not hard-code a "fast" tier ID; valid named tiers must be taken from the model's serviceTiers metadata. No account-backed catalog was queried, so availability of Fast for current account/models is **unverified**.
- **Source fact:** Harness client CodexAppServer.run() sends role model and effort in turn/start, but accepts no service-tier argument and emits no tier field [src/codex-app-server.js:829-837, 1043-1055]. src has no serviceTier, service_tier, or Fast setting. Therefore a UI switch alone would not affect execution.
- **Recommendation:** Add a typed local model-discovery adapter that exposes per-model effort/tier metadata; pass validated role settings through a service-tier parameter. A user-facing Fast on choice should resolve to an advertised tier ID; Fast off should use the documented default for a turn. Keep unavailable/unqueried tier state explicit; do not hard-code a tier name from this schema alone. Temporary protocol evidence may disappear; regenerate with the command above when needed.

A project total cap of 12 is proposed, noncore roles are on-demand, and agents should be chosen dynamically by the lead from role/project capacity. Do not require launching the full configured pool for each assignment. Listed defaults sum to 11 including lead, so the meaning/allocation of the remaining project-cap slot is for root to finalize. Earlier owner/lead steering establishes finite configurable per-role capacity (initial default 4), backlog independent/unbounded by that value, separate overall cap, and no unlimited mode in the first release.
