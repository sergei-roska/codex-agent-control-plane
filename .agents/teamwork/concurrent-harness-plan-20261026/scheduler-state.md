## Current graph and durable ownership

`LeadOrchestrator.run()` accepts a goal and runId, refuses a preexisting checkpoint for that run, then invokes the graph (`src/lead-orchestrator.js:449-459`). LangGraph `thread_id` is the runId (`321-327`); the state schema is `LeadState` (`src/lead-graph.js:736-799`). It holds one planning trajectory: goal, runId, round, outcomes, pendingAssignments, one batch, review obligations/recovery, decisions, budgets, and final state. `decide -> dispatch -> collect -> verify -> decide` is the ordinary cycle (`src/lead-graph.js:4514-4545`). This is a checkpointed graph for one run, not a durable ready-work queue.

SQLite roles currently include:

- LangGraph SQLite checkpointer and A2A SDK `tasks` table share the state DB connection (`src/durable-store.js:53-90, 132-158, 247-253`). The checkpointer persists graph state by runId thread.
- `dispatch_journal(attempt_id PK, run_id, assignment_id, role, sandbox, context_id, task_id, state, result_json, timestamps, objective_sha256)` plus run index (`src/durable-store.js:93-115`). Legal source transitions are submitting -> submitted -> finished, with idempotent identical finish replay (`301-344`).
- `session_threads(context_id PK, thread_id, codex_home, token/window/profile data, rollovers, run_ids_json, timestamps)` stores one lead Codex thread per dashboard context/session (`src/session-threads.js:3-30, 52-67`). A session can link multiple runs; it is not the graph run/thread ID.
- `staging_events` is append-only assignment/outcome/event evidence (`src/staging-log.js:15-38`); `transient_recovery(run_id PK, attempts, next_attempt_at, category, cause, checkpoint_id, state, updated_at)` stores delayed run resume (`src/transient-recovery.js:44-80`). `writer_lanes` stores lane lifecycle (`src/writer-lanes.js:24-45`); writer admission is workspace-wide and unique for active/unresolved executions (`src/writer-admission.js:40-44, 58-80`). None of these stores a general dependency-ready queue.

## Multi-project boundary

Source has no global work scheduler or shared backlog/capacity arbiter. Launcher project records start separate `server-bootstrap.js` children with project-specific workspace, port, and `CODEX_A2A_STATE_DB` (`src/launcher-projects.js:338-340,457-465`); each server opens and locks its own state DB, then acquires a workspace lock (`src/server.js:850-852`). Thus independent project DBs and local run/checkpoint/review ownership already exist, but no source mechanism coordinates provider-wide or cross-project worker capacity/fairness. The workspace lock is a hard shared-resource exclusion: it keys on Git common-dir when available, explicitly covering nested/aliased workspaces, otherwise canonical workspace path (`src/durable-store.js:220-242`). Two server instances pointing to the same repository/common-dir cannot both start, even with different DBs. This is an existing blocker for concurrent service instances on workspace aliases; it is not a global scheduler.

Recommended ownership: keep objective queue, dependencies, assignments, review obligations, reconciliation, and fairness local to each project DB and lead. Permit one lead/scheduler per project to advance independently; no project's pending verifier/auditor, unresolved writer, or owner pause should hold another project's graph. Put any genuinely shared provider/account concurrency and fair-share arbitration above project schedulers as a small global capacity service/lease table, keyed by provider/account/model or other real shared resource, not project identity. Workspace admission remains project/workspace-local and must stay exclusive when two projects alias one underlying repository. Prefer separate worktrees/repository identities for simultaneous same-repo projects, or explicitly retain the current lock as a guard and report the project blocked. Provider quota pauses should consume/release capacity fairly and remain local in state, with the global arbiter scheduling around them.

Terminology and identity:

- **Run**: one LangGraph trajectory and checkpointer thread, keyed by runId. **Session**: dashboard A2A contextId, optionally linked through `session_threads` to a continuing lead provider thread across runs.
- **Round**: dispatch decision sequence counter, incremented when a new batch is created (`src/lead-graph.js:3414-3424`). It is ordering/progress, and caller maxRounds limits dispatch rounds, not worker count (`lead-orchestrator.js:17,220-221`; `lead-graph.js:1975-1976`).
- **Assignment**: logical work request in a lead decision, ID `${runId}:r${round}:a${index}` (`src/durable-store.js:29-35`). **Attempt**: one worker turn under that assignment, normally `:t1`; usage continuations use a `:cN` assignment suffix and new attempt/context (`src/lead-graph.js:4077-4088`). **ContextId**: deterministic UUID-shaped SHA-256 of attempt (`durable-store.js:37-47`), used to find/deduplicate A2A task on uncertain submission.
- **Batch**: all assignments of one valid dispatch decision, each with pending/submitted/finished status and fixed group. **Wave/group**: `executionGroups` groups only consecutive equal non-null wave values; null always makes a singleton group (`contracts.js:895-909`). Repeating a wave after another wave does not merge it.

## Concurrency, serial barriers, replay

Dispatch contract caps one decision at 4 assignments (`src/contracts.js:8,1050-1056`). No per-role count restriction was found. Same-role assignments are therefore legal, including repeated reviewers, subject to distinct scopes and review constraints. Reviewers cannot share an execution group with writers; same-checkpoint auditor must be in a group after its verifier; context must match (`contracts.js:925-984`). Distinct checkpoint reviews can share a read-only group. Harness dispatch submission and collection use Promise.allSettled, but the graph waits for all submitted tasks to become terminal before it can proceed (`src/lead-graph.js:3736-3744,3747-3774,3786-3794`). Early completion is not surfaced to planning.

With `parallelWriters`, one group at a time runs; its next group is submitted only after earlier group items are finished (`lead-graph.js:3512-3524`). Writable workers can edit isolated lanes concurrently: lane-eligible worker turns bypass normal writer admission (`src/a2a-role-service.js:860-930`), while lane integration itself acquires workspace-wide admission and shared-tree mutex (`writer-lanes.js:416-450`). Without this config, non-readonly items are submitted one at a time. Read-only batches without review role and explicit waves are submitted together (`lead-graph.js:3416-3421`). Review dispatch is still within the same 4-item batch and wave/group logic; verifier then auditor is the only same-checkpoint sequence. Ordinary dispatch stops for lead planning after full submitted set -> verify -> decide. Critical gates, owner/human pauses, unresolved writers, review/reconciliation, acceptance, and budget recovery add further barriers.

Crash/replay facts: dispatch records `submitting` before sending A2A (`lead-graph.js:3303-3342`); on resume it queries by deterministic context. If no task is found for a writer in that window, it records outcome unknown and will not resend (`3333-3341`). After a send error it immediately looks up context; absent/failed lookup leaves writer effects unknown (`3371-3388`). Submitted journal rows are polled, finished rows return stored result; conflicting task IDs or changed finished results are rejected (`durable-store.js:324-344`). A2A task identity and journal cover attempt effects; checkpoint contains scheduler plan/state. These are separate durability layers, so recovery must reconcile their identity rather than assume one atomic transaction.

## Redesign extension points and proposed ownership

Reuse the existing SQLite DB, `DispatchJournal` transition discipline, append-only `StagingLog`, `SessionThreads`, LangGraph checkpointer, A2A context lookup, and lane/admission semantics. Add an explicit durable objective/task queue owned by a scheduler service, with task/dependency rows and atomic claim lease/fencing rows; do not treat `LeadState.batch` as a backlog. Suggested narrow interfaces: `enqueueObjective`, `claimReady(capacity, roleCapacity, now)`, `recordStarted(taskId, attemptId, workerId, contextId)`, `completeAttempt(attemptId, resultRef)`, `releaseClaim(reason)`, `listBlocked(objectiveId)`, and append-only scheduler events. Scheduler should own claims/capacity/retries; planner owns decomposition and dependency links; worker service owns execution; acceptance/reviewer policy owns promotion to accepted. Persist the immutable assignment contract/pins before claim/send, and have completion events wake the scheduler/lead without waiting for sibling attempts. Model-level planning should return bounded candidate tasks; deterministic admission validates prerequisites, scoped write conflicts, checkpoint gates, budget, owner controls, and capacity.

Redesign invariants to carry forward:

1. Stable objective/task IDs survive replans; attempts are distinct, monotonic, and each has one deterministic A2A context. Idempotency key prevents duplicate accepted execution.
2. Claim is atomic, leased, fenced, and bounded by global plus per-role capacity; expired claims reconcile remote A2A task and workspace effects before retry.
3. Dependency readiness is explicit and durable; task completion wakes dependents immediately. Candidate state is immutable/versioned so stale planners cannot overwrite newer queue state.
4. Completion is per attempt, not per batch. Terminal receipt is recorded once; a planner may run while independent work is active, but only from a consistent queue/review/target snapshot.
5. Writers remain isolated during turns; integration remains serialized or conflict-checked. Unresolved effects fence dependent writers and reviewers.
6. Review receipt binds exact candidate identity, checkpoint/scope, immutable pins, and target. Same-checkpoint auditor requires accepted verifier; unrelated reviews may run concurrently under reviewer capacity.
7. Cancellation, owner pause, quota/transient retry, and process restart preserve claims and truthful unknown states. Never silently resubmit an uncertain writer.
8. Four-item lead decision limit can remain a planner response bound; it must not be the durable queue capacity or concurrency cap. Round becomes audit metadata, not a readiness gate.
9. Project scheduler state and review gates are isolated by project. One lead per project can schedule concurrently with other projects; cross-project blocking is limited to explicitly shared workspace/resource locks and provider/account capacity. Global fairness must not merge project review policy or reconciliation ownership.
