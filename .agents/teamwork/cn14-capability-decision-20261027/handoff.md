# CN14 trusted verifier capability decision

Verdict: APPROVE the narrowed design below as an implementation entrypoint. This is a design decision, not a CN14 source or runtime gate. Evidence: read current source and installed experimental schema; no live service/model call or product edit.

## Decisive facts

- Read: `src/task-executor.js:99-108` calls `checkSpecialistRequest` before transport and requires `allowedFiles` to equal `productWritePaths`. `src/contracts.js:783-785` rejects empty `allowedFiles` for a workspace-write role. `src/candidate-review.js:312-318` creates frozen review tasks with `productWritePaths: []` and task-level scratch roots. The current path cannot send one as a configured writable verifier.
- Read: `src/a2a-role-service.js:704-710` validates independently, and `:371`, `:860-931` derive writer/lane admission from the static role sandbox. A capability-aware validator alone would still serialize this scratch-only review with product writers or create a writer lane. The capability must be selected before validation and admission. Keep all legacy behavior when no trusted capability resolves.
- Read: `src/a2a-role-service.js:1003-1019` passes workspace or lane as cwd and project workspace as `permissionWorkspace`. `src/codex-app-server.js:864-886` ignores an explicit policy under modern inherited named permissions and reconstructs broad legacy roots from `permissionWorkspace`. The installed `ThreadStartParams` and `TurnStartParams` schemas prohibit `permissions` with `sandbox`, respectively `sandboxPolicy`.
- Read: `src/codex-app-server.js:969-1038` pins execution policy per loaded thread and can update thread settings. `src/codex-app-server.js:1441-1462` declines client-side approval requests, but explicit scoped runs still need to prohibit inherited broad profile use and inherited broad thread reuse. `src/candidate-review.js:449-475,478-533` materializes and verifies the candidate and settles only after trusted attempt identity, input manifest, zero product writes, passed checks, and quiescent effects. `:635-644` already permits independent reviews with distinct scratch roots.
- Read: `CodexAppServer.run` owns thread creation immediately before `turn/start`; it has no public prepare-thread API. This verifier capability does not solve the separate CN14 lead-planner preadmission physical-thread requirement. Package A must obtain a narrow host-owned prepare/bind API or equivalent before lead planning admission, with Package B owning any AppServer API edit. Do not treat an invented thread ID as a provider binding.

## Minimal host API and wire contract

1. Add a host-owned `resolveVerifierCapability(claim)` dependency to the concurrent engine/A2A registration. Input is the exact `{projectId, objectiveId, taskId, attemptId, fencingToken, providerContextId, requestDigest}` claim, with A2A task context supplied separately. The resolver reads the authoritative shared DB and returns an immutable capability only for a live, pinned `kind: review`, `role: verifier`, `productWritePaths: []`, `publicationAuthority: denied` attempt bound by `CandidateReview.bindClaimedAttempt`. It must compare task revision/digest, owner generation, selected settings digest, claim lease/fence, candidate ID, manifest digest and review context. Materialize and verify a frozen candidate outside the project workspace, and allocate one private scratch root per attempt. Canonicalize paths, reject symlinks/overlaps/duplicates and ensure neither root is inside the live workspace. Do not treat chmod as confinement.
2. Add `validateSpecialistRequest(request, role, {capability})` as a host-only validator extension shared by TaskExecutor and A2A. The exception is exact: verifier, live matching capability, `allowedFiles: []`, equal objective and request digest, no product writes. All other requests continue through existing `checkSpecialistRequest` unchanged. Do not add `trusted`, path, or policy fields to request JSON. The capability is resolved independently at both boundaries from durable state; equality of caller metadata alone grants nothing.
3. Wire A2A message metadata only as lookup claims: `{projectId, objectiveId, taskId, attemptId, fencingToken, requestDigest, capabilityId}` plus existing `contextId` and optional `threadId`. `productWritePaths` and `scratchWriteRoots` in metadata remain diagnostic only. On receipt, A2A compares the SDK context ID, endpoint role, normalized JSON digest, and all claim fields against its trusted resolver. An unknown, stale, duplicate-conflicting, or unresolved claim fails before `appServer.run`. Since SDK task IDs are generated remotely, bind the generated external task ID to the attempt after admission rather than equating it to the durable task ID.
4. For a resolved capability, bypass the static writer/lane admission only for that invocation, never globally for the role. Keep a separate per-attempt scratch reservation and process/fence tracking; unknown effect or failed reconciliation retains the fence and scratch. Legacy verifier requests retain their current review/staging/admission rules. Do not let the legacy workspace-based review target substitute for the frozen candidate identity; use the candidate manifest/context for scoped receipt evidence.
5. Add an explicit `CodexAppServer.run` host-scoped policy argument, accepted only from A2A's trusted resolver path. Call with `cwd` under the private scratch root, `permissionWorkspace` equal to the configured project only to read the inherited approval choice, and `sandboxPolicy: {type:'workspaceWrite', writableRoots:[scratchAbs], networkAccess:<existing verifier IPC requirement>, excludeTmpdirEnvVar:true, excludeSlashTmp:true}`. Send `thread/start` or `thread/resume` with `sandbox:'workspace-write'` and no named `permissions`; send `turn/start` with that exact `sandboxPolicy` and no named `permissions`; keep the resolved inherited `approvalPolicy` and `approvalsReviewer` fields. Never fall back to `nativeSandboxPolicy(projectWorkspace, ...)`, the named profile, `dangerFullAccess`, or a broad thread on this path. Require a fresh thread or a durably capability-bound thread with identical policy digest, candidate/attempt identity and scratch root; an unknown resumed policy fails closed. Check candidate via its absolute path before and after the run. Pin actual provider thread identity using `CandidateReview.pinObservedThread` and preserve TaskExecutor's remote/context mapping.
6. The receipt adapter must derive `inputManifestDigest`, `candidateId`, check pins and outcome from trusted candidate/review state plus observed run/report/process evidence, not remote metadata or report assertions. Record `productWrites: []` only after the sandbox and delta/effect evidence agree. On any candidate drift, policy mismatch, process uncertainty, or unknown send outcome, return unknown/blocked and do not settle a passing receipt. `CandidateReview.settleReceipt` remains the final authority.
